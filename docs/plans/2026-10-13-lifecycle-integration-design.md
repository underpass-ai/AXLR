# Lifecycle integration with KMP and MADE (13 Oct 2026)

AXLR is meant to use KMP as its primary memory and MADE as its procedure engine. On 13 October 2026 a fresh install on a new Mac showed that neither fits yet: the install predated #115, so no engine was configured at all, and once configured the model (claude-haiku-5.5) still had to run KMP's protocol itself, from a store that held none of the project's memory. This design makes the console own the lifecycle so that a small model has one obvious thing to do at each moment and the transcript proves it.

Revision 5, same day: the decisions below follow Tirso's answers to the [lifecycle questionnaire](2026-10-13-lifecycle-vision-questionnaire.md), answered in full in eight rounds of chat (the K5 extension included); the two symptoms of the Mac are confirmed as two problems with two fixes (A8). The main changes from revision 1: every session is a MADE ceremony, MADE is the execution record, Jev decides what the session settles, a clean install is autonomous and fully configured without questions, and the model's context is bounded in tokens with a successor session instead of compaction.

## What is wrong today

Each point below is checkable in this checkout or on this machine.

1. **Three memories for one project.** The installer pins `KMP_MCP_DATA_DIR=$XDG_DATA_HOME/kmp/default` ([installer.go](../../tui/adapters/enginesetup/installer.go)), one store for every workspace of the user. KMP 0.25.0's own precedence is `KMP_MCP_DATA_DIR`, then the nearest project root (`<repo>/.kernel`, shared by its worktrees), then the saved selection, then the per-user default (`kmp-mcp info`). The other hosts on this machine therefore write to `<repo>/.kernel`. `kmp-mcp memories --json` on 13 October: the global store holds `project:AXLR` (30 events) and `project:axlr` (27 events); `AXLR/.kernel` holds `project:AXLR` (7 events). The lower-case about is AXLR's `ProjectAbout` ([memory_about.go](../../tui/application/memory_about.go)) since 10 October; the capitalised one is what KMP's hosts and the person use. A fresh clone on another machine starts from an empty global store even when the repository carries its bundle (`.kmp/memory.jsonl`, which `kmp-mcp export` maintains and `kmp-mcp import` restores); in this checkout the bundle exists and is untracked.

2. **The protocol is the model's job.** In a normal session the console wakes nothing and registers nothing. The system prompt and the `axlr:axlr-session` skill (4 433 bytes, two `axlr_skill` pages) ask the model to call `axlr_session`, discover KMP schemas with `axlr_tools`, start `kmp_guide` with a registration key, keep `agent_id` and `context_id`, wake the about, finish pages, run one `kmp_relate` comparison after the second prompt, set a title, and record what it settles. A glm-5.3-flash session (`e45c46dc…`) made 35 `axlr_tools` calls, 3 `kmp_guide` registrations and 2 `kmp_curate` calls over 15 prompts; a claude-haiku-5.5 session (`c33e8e86…`) made 16 `axlr_tools`, 3 `kmp_relate`, 2 `kmp_wake` and 1 `kmp_guide` over 54 prompts. Only ceremonies get a console wake ([ceremony_driver.go:259](../../tui/application/ceremony_driver.go)).

3. **Nothing records the session as a procedure.** The transcript keeps messages, calls, the decision (`approve`, `auto_approve`, `deny`) and outcomes ([pending_tool.go](../../tui/domain/pending_tool.go)); the person's denial reason survives only as the tool result's text; no action carries a reason from the model. MADE sees a session only when a mode starts a driven ceremony. KMP receives a ceremony's terminal observation ([ceremony_driver.go:796](../../tui/application/ceremony_driver.go)) and whatever the model volunteers through `axlr_remember` after a `[AXLR · memory]` reminder that costs one request per working turn.

4. **MADE's write surface reaches the model.** Both engines register with `allow_tools: ["*"]`, no mode hides a plugin tool ([work_mode_policy.go](../../tui/domain/work_mode_policy.go) names only `kmp_write_memory`), and with `autonomous: true` every plugin call runs without a card ([approval_settings.go:99](../../tui/adapters/storage/approval_settings.go)). In the glm-5.3-flash session above the person asked for a parallel test ceremony, and the only way to run it was for the model to design, publish, start, claim, complete and transition it through the bridge (3 `made_claim_ceremony_step`, 4 `made_complete_ceremony_step`, 2 `made_apply_ceremony_transition`), with no stall reminder, no check run by the console and no outcome record. The driver reports no host status, renews no lease and records no handoff ([engine.go](../../tui/adapters/ceremonyhost/engine.go)).

5. **A fresh install is not verified.** Setup installs the engines, syncs the guide, writes `mcp.json`, prepares MADE and opens the console. Nothing restores a bundle, nothing checks that the project about answers, and `/mcp` does not say which store a session opened or why.

The two Mac symptoms have different fixes: "no memory at all" is 1 and 5; "the model fumbles the protocol" is 2 and 4.

## Principles

- **Every session is a MADE ceremony.** The console starts an `axlr_session` instance when a session is created and completes one `turn` step per prompt. MADE is the record of execution: what was asked, what was done, with what result and why.
- **KMP holds what a session settles, under three abouts with three owners** (A1, A4). The console owns `ws:<session-id>`: results, closes and ceremony outcomes, actor `axlr`, no card. Jev owns `project:<name>` and `user:<name>`: what a turn settled, the person's preferences and corrections, and the `supersedes` that keep them current, written by the console with evidence. The model writes `project:<name>` only where Jev is not configured, with `axlr_remember`. The person has `/memory save` and `/memory forget`, no write command of their own. Nothing reaches the project about without evidence.
- **The console owns bookkeeping; the model owns the work and its reasons.** Registration, context, wake, store, instance, claims, completions, status and journal are console actions. The model gives every side effect a `why`, may set the session's title and an explicit about, and records what it settles when Jev is absent.
- **One checkable rule per moment.** Each row of the lifecycle table is either something the console did (visible in the app log, MADE and KMP) or exactly one tool call that proves the model did it.
- **Memory lives with the project.** The store of a git workspace is the repository's `.kernel`, shared with the person's other hosts; the committed bundle restores it on a new machine.
- **Zero model requests for bookkeeping, at most 1 KB of stable prompt, three console MCP calls per turn** (claim, complete, the `ws:` write): the spike of 13 October showed MADE re-claims a repeating step inside its state with no transition per turn, so the `next_turn` transition went away. Status reports, heartbeats and Jev's writes are not counted.
- **Never translate or rewrite what the person or the model wrote.** Extracts are stored as written, with secrets redacted.

## Decisions

### D1. The store of a git workspace is `<repo>/.kernel`

Today one per-user store is pinned at install so KMP cannot "select a different default store by accident". Decision (B2, B3): the console resolves the store per workspace at launch, explicitly, and pins it with `KMP_MCP_DATA_DIR` for that process: an operator value in `mcp.json` `env` first; then `<git toplevel>/.kernel` for a workspace inside a git checkout, created with KMP's self-ignoring `.gitignore` and the global store's configuration files (B7); then the per-user default outside git. On a machine with no configured global store (the Mac), AXLR writes the ready-to-use set itself: `rerank.json`, `wake-focus.json`, `write-expansions.json` and `curate.json` with KMP's documented defaults, and `typesafe.json`, `ask-judge.json`, `judgement-book.json` and `write-relations.json` (lifecycle `jev`) only when a TypeSafe key is configured, since they call Jev. The exact values are copied from this machine's global store when the phase lands and reviewed against KMP's documentation. Two engines on one `.kernel` are supported (Tirso, as KMP's author, 13 October), so AXLR shares the live store with Claude Code and Codex in the same checkout. The protection is kept by making the selection visible: the startup line and `/mcp` show the path and the reason (`operator`, `project`, `user`). The installer stops writing `KMP_MCP_DATA_DIR`. An existing entry that has it is read in two ways: a value equal to the per-user default path (`$XDG_DATA_HOME/kmp/default`, what the installer wrote until this change) is the old pin and the console overrides it for a git workspace, saying so once in the startup line; any other path is the operator's choice, wins, and `/mcp` says so. Shared engines are keyed by the launch environment ([run_engines.go](../../tui/cmd/axlr-tui/run_engines.go)), so a per-workspace store means one KMP process per workspace.

No migration (K3), and the duplicated abouts of this machine are deleted rather than merged (C2): `project:AXLR` and `project:axlr` leave the global store, `AXLR/.kernel` is untouched. KMP has no per-about delete, so it was a full export kept as backup (`default-backups/default-full-20261013.jsonl`, 525 events), an export of the other 22 abouts (468 events), the old store moved aside to `default-retired-20261013` and a re-import into a new `default` with its configuration files copied; done by hand with Tirso's go-ahead on 13 October, outside any phase. What the saved sessions hold stays where it is, and only new sessions follow this lifecycle. `kmp-mcp import --from <global store> --about <about>` (imports an absent about, leaves an identical one alone, extends an exact prefix, refuses a different history) is documented in the KMP runbook for whoever wants to move a project's memory by hand. Nothing is deleted.

Bundle (B5): imported at workspace open only into an empty store; never exported or committed by the console. `/memory save` exports on demand (`kmp-mcp export`), and the person decides whether `.kmp/` is tracked.

### D2. One canonical about per workspace, case preserved

Decision (C1): `project:<name>` where `<name>` is, in order, the `project:*` about of the repository's bundle (several: the one equal to the directory's name ignoring case, else the one with most events, said in the startup line); else the repository directory's base name with its case (`/home/me/AXLR` gives `project:AXLR`); else the workspace base name. Runs of spaces become `-`; nothing is lower-cased. The lower-casing of 10 October is retired. A repair or improvement session (C8) works in the disposable clone's own `.kernel`, under the about of the repaired repository (`project:AXLR`), importing the clone's bundle when it has one, so the repair's memory belongs to the project repaired rather than to the workspace that asked for it. The clone's directory has a generated name, so the about is derived from the repository's name in `repair.repository` (`underpass-ai/AXLR` gives `project:AXLR`, case preserved), with the clone's bundle about winning when it has one; `repair.about` in settings stays as the operator's override, as `KMP_MCP_DATA_DIR` does for the store, and [self_repair.go:391](../../tui/application/self_repair.go) stops lower-casing. For a store that holds both spellings, the first-prompt wake uses `dimensions.scope: abouts` with both until the person merges them. The model may still save an explicit about with `axlr_session` when the person or the repository's instructions name one (C9), and the saved label wins.

`ws:<session-id>` keeps its spelling and meaning (C3, confirmed): this workspace's session, with the workspace path as a label. It is the about of the session's results and of ceremony outcomes (K2).

### D3. The console runs KMP's protocol; the model gets two host tools

Decision (C4, C5, D1, D2, G1): registration once per store and machine, the agent named `axlr@<host>` in its attributes (`registration_key: axlr:<install-id>`; KMP keeps agents in the store's `agent-users.sqlite3` and gives each its own random name, so a new store means a new registration; the agent id is kept per store in the state directory), one context per session (`context_key: axlr:session:<id>`), `context_id` injected by the console into every bridged `kmp_*` call and `axlr_remember`; a successor session (D10) opens a new context with the same agent. The first prompt carries the project wake as a `[AXLR · recall]` note appended the way `StartTurnUseCase` appends ceremony step notes and repair notices, so the system prompt keeps its byte-stable prefix. A resumed session gets `ws:<session-id>` woken too.

The wake (D3, D4): the project about and `user:<name>` (F6, the person's preferences and corrections, which Jev or the model record there as `preference` and `feedback`), the sections ceremonies already keep (`current_state`, `open_loops`, `next_actions`, as prose), on the first prompt and again only when a later prompt's intent differs from the one last woken: the console compares the new prompt with the woken intent (Jev when configured, else a lexical comparison) and appends a fresh note when it changed.

`axlr_recall` is a new host tool, `{question?, about?, since?, mode: ask|wake|history}`, mapped to `kmp_ask`, `kmp_wake` and `kmp_time` (D8: not inspect or trace, which stay raw through the bridge) with the session's about, context and a bounded budget, answered compactly as `axlr_remember` answers. Comparisons between abouts (D7) run only on demand with `/memory compare <about>…` (`kmp_relate`); when a wake exposes related abouts, Jev may propose one as a console note and the person decides. `axlr_remember` gains an optional `summary_en` (E13) whose description says a strict store needs it for a non-English memory. Raw `kmp_*` through `axlr_call_tool` stay reachable except `kmp_guide` (G6): registering an agent, changing store or context is the console's alone, and the bridge refuses it with "the console manages KMP's identity".

Concurrency (C6, C7): sessions open at once in one workspace share the store, the about and the agent, each with its own context and its own MADE instance; a worktree shares the store and about of its checkout with its own path as the `ws` label. The compact profile (G5) runs the same cycle with lower caps: a 1 KiB recall note, `why` still mandatory, `axlr_recall` offered.

Dropped from the model's duties: `kmp_guide`, `context_id`, page finishing for bookkeeping, the startup `kmp_relate` comparison (`/memory compare` on demand). Kept: the title after the second prompt (G3) and the explicit about (C9). The `axlr:axlr-session` skill is replaced by the paragraph in D8.

### D4. The session is an `axlr_session` ceremony; its turns are the record

Decision (H1, H8, E1, E9): the console publishes `axlr_session` 1.0 with the other definitions: states `OPEN` → `DONE` or `ABANDONED`, one host-callback step `turn` that repeats, claimed when a prompt arrives and completed at turn end with this output:

- `prompt`: the person's text, first 500 bytes; `prompt_index`: the transcript index;
- `answer`: the model's final text, first 500 bytes, and `answer_kind`: `answered`, `changed`, `asked`, `refused`, `paused`;
- `actions[]`: every side effect of the turn with `tool`, a digest of its arguments (path and mode; the command line; the plugin and tool; a forged tool's name and version, E14), the model's `why`, the decision (`approve`, `auto_approve`, `deny`) with the person's reason, the outcome class (`completed`, `error`, `denied`, `over_budget`), `occurred_at`, and for commands the exit code and the redacted tail of their output, up to 4 KiB as the ceremony check keeps (E5);
- `memories[]`: each accepted memory write (about, key, ref); `ceremony`: a driven instance started or advanced in this turn, with its state;
- `mode`, `model`, `about`, `title` when they changed; `reads`: the count of reads; `cost`: tokens and USD.

Reads (`local_read`, `local_search`, `local_list`, `axlr_tools`, `axlr_history`, `axlr_skill`, `axlr_session`, and bridged reads) are counted, not listed. Values that look like keys or tokens (`sk-…`, `ghp_…`, `AKIA…`, `Bearer …`, `*_KEY=…`) are replaced by `[redacted]` (E11) in arguments and output tails alike. The entries are flat, with labels and the MADE ref, and no relations between them (E7); `follows` and `verified_by` written by the console are a later refinement.

KMP gets the results only (H8, E1, confirmed in the second round): one `turn` entry per turn under `ws:<session-id>` with the files written, the commands and their exit codes, the external calls with effect, the memories recorded, the decisions with their reasons and each action's `why`; its evidence is one line per action (E8): the MADE step ref ("MADE axlr-session-<id> step turn #N"), the path or command, the exit code and the file's hash after the write; the prompt and the answer live in MADE alone. Written with `kmp_write_memory`, `actor: axlr`, English `summary` and `summary_en` by the console, labels `{project, ws, session, mode, model}`, per-action `occurred_at`, key `axlr:turn:<session>:<message-index>`. A turn with no result (an answer from reading) writes nothing to KMP. The console writes with `kmp_write_memory` only, never `kmp_ingest` (E6). When a write the console makes for the model (`axlr_remember` with links, Jev's `supersedes`) comes back `needs_review` and every link points at a ref the session's wake exposed, the console commits the continuation itself; a link to a ref the wake did not show goes back to the model for review as today (F4).

MADE bounds `repeat.max_iterations` to 1 000 (the spike of 13 October: 10 000 was refused, 1 000 published with digest `ac1273df…`). `axlr_session` 1.0 repeats `turn` up to 1 000 times inside `OPEN` and closes through `closed`, `abandoned` or `exhausted`; when a claim is refused for exhaustion the console opens `axlr-session-<session-id>-2` with the predecessor as an input and goes on. The same spike showed that two open instances of one actor coexist and that a second claim while a lease is live is refused ("step lease is still active"), so an interrupted turn is completed with its stored fence before any new claim.

A driven ceremony runs as its own instance while the session's `turn` stays claimed; the turn record names it.

The `why` is mandatory (E2): a side-effect call without it is refused with "give why: one sentence, what this call is for", which the model answers in its next request. The person's `why` (E3) is the denial reason that exists today, an optional note on approve (`N` on the card, one line) and a free note per turn with `/why <text>`, all three stored in the turn's record in MADE and in the `ws:` entry.

Console writes raise no card (`callPlugin` in [plugin_output.go](../../tui/adapters/ceremonyhost/plugin_output.go) calls the tool runner outside the agent loop) and never enter the transcript. When an engine is down (A2, E10) the console queues the calls on disk under the state directory, keyed, shows it in the header and replays them at the next turn or start.

A session does not start without both engines (A2). This reverses a documented property: [getting-started.md](../getting-started.md) ("The console can start without either engine") and [product.md](../product.md) ("The console can still work without them") change with phase 5, together with D9, because until then an existing install may lack `axlr_session` (only `P` or the installer publish a pinned definition) and a hard refusal would lock every such install out. In phase 2 a session whose MADE is missing, down or unprepared runs its turns anyway, says so once in the app log, and keeps its instance state for the next prompt. Setup's offer to install the engines becomes a requirement in phase 5: when a download fails, setup says that the console needs both and exits with the [KMP](../runbooks/kmp.md) and [MADE](../runbooks/made.md) runbooks for a manual registration; `axlr-tui` started with neither connected refuses with the same line. A non-interactive start (a pipe, `--model`, CI, `axlr-serve`) installs and configures exactly the same without asking anything (B12): the model key comes from the environment or the start fails, engines, stores and the complete configuration are created, and Jev is on only when `TYPESAFE_API_KEY` exists.

The mandatory `why` applies to every bridged `axlr_call_tool` and `axlr_run_tool` as to the local side effects, reads included (E14: the exemption for `readOnlyHint` reads was offered and not taken), under the compact profile too (G5); each refusal costs one request, which the tool descriptions and the prompt line about `why` are there to avoid. The asymmetry is deliberate: `local_read`, `local_search` and `local_list` need no `why` because they are the console's own and change nothing, while a bridged call reaches another program; `axlr_recall` is a host tool and takes no `why` either.

There is no checkpoint any more (D10): a session that reaches the token cap continues in a successor whose first prompt carries the recall of the previous session, so nothing quotes omitted requests. `axlr_history` still pages the previous session's transcript when the model names its id, which the recall note gives.

### D5. Jev decides what a turn settles

Decision (F1): after the turn record is written, and only for a turn whose record has at least one side effect, check or memory write (a greeting or a question answered from reading costs no Jev call), the console asks Jev (`axlr_judge`, [judge_final_check.go](../../tui/application/judge_final_check.go)) one question with the record as state: did this turn settle a decision, constraint, fix or outcome worth reusing in this project, and if so which, each with kind, text and the actions that are its evidence. The console writes each proposal with `kmp_write_memory` to the project about, or to `user:<name>` when its kind is `preference` or `feedback` (A1, F6), actor `axlr`, evidence the MADE step ref plus the action digests, labels `{session, judged_by: jev}`, key `axlr:settled:<session>:<message-index>:<n>`, English summary written from the proposal without rewriting the quoted text. No card. Where Jev is not configured, the model's `axlr_remember` works as today with `summary_en` when it wrote in another language, and the `[AXLR · memory]` reminder is sent only for a turn that wrote a file or ran a check (F2), never for reads or for the five-local-calls rule of today. That, with one `why` per action, is all a small model is asked beyond its work (A6); title and explicit about stay allowed, not required.

Jev also receives the live memories the wake exposed for the about: when it finds that a turn's result contradicts or replaces one of them, the console writes the `supersedes` or `corrects` relation with Jev's why and the turn's evidence (F5), so the project about keeps one current answer without the model handling links. At session close nothing more goes to the project about (F3): the close completes the instance and writes `session_closed` under `ws:<session-id>`.

Ceremony outcomes (K2) stay under `ws:<session-id>` as today; they reach the project about only through Jev's judgement of the turn that ended them. A blocked or cancelled ceremony (H10) keeps its state in MADE and its outcome in `ws:<session-id>`, and the console proposes the next step to the person in the conversation: repeat with another check, change mode, or open a repair.

Retention (E15, E16): nothing is deleted; closed `ws:` abouts enter no wake unless asked; `/memory forget <ref>` closes an entry with `valid_until` or a `supersedes` relation and never removes it.

### D6. MADE: reads and design for the model, everything else console-driven

Decision (H2, H4, H5, H7): the model sees `made_get_help`, `made_discover_capabilities`, `made_list_*`, `made_get_*`, `made_read_*`, `made_stream_*`, `made_search_*`, `made_design_ceremony`, `made_validate_ceremony_draft`, `made_explain_ceremony_draft`, `made_diff_ceremony_definitions`, `made_render_agentic_system_diagram`, `made_generate_ceremony_report`, `made_verify_ceremony_journal`, and nothing that starts, claims, completes, transitions, cancels, pauses, resumes, runs, approves, defers, grants, revokes, publishes, registers, deletes or uploads. The filter lives in `ModelTools` ([host_tool_definitions.go](../../tui/application/host_tool_definitions.go)) by plugin id `made` and verb name, and `axlr_tools` discovery applies the same filter, so the model never sees a hidden verb's schema; the console's `callPlugin` path is unaffected. A hidden verb through the bridge is refused with "the console runs ceremonies: ask the person for /ceremony". With `made` at `auto` (B11) the visible reads run without a card.

Only the console publishes (H4): `P` in `/mcp` and `/ceremony publish <draft>` with the temporary install grant; the model designs and validates. `/ceremony <definition> [version] [brief]` drives any published definition with the generic loop (claim, instruction, `axlr_step_done`, complete, transition, stall reminder); the instruction of each step is what `made_explain_ceremony_draft` returns for it (H3), passed to the model as the step note, with the console adding only the `axlr_step_done` fields the step's declared outputs require. Whether that explanation is enough for a small model is checked in the phase-4 tmux run; whether the verb accepts a published definition and version rather than a draft is a spike, with `made_get_ceremony_definition` rendered by the console as the fallback. MADE's human guards and AXLR's approval cards stay separate (H7).

Host visibility (H5, H6): `made_report_ceremony_agent_status` at claim (`running`), hand-back (`finished`), stall (`blocked`) and every 5 minutes (`heartbeat`), with `host_agent_id` the install id, `host_agent_incarnation` the console run id, `logical_worker_id` the session id, and the requested and actual model; `made_renew_ceremony_step_lease` at three quarters of the lease; `made_record_ceremony_host_handoff` when a resumed instance last reported from another incarnation, with the previous console's run id, host name and the time of its last report as the declaration's evidence (H6). `made_register_agent` is for councils and is not used for host identity; councils and agentic systems stay outside the console's lifecycle (H9): the model may read them, AXLR is no council's agent.

### D7. A fresh install ends with memory verified

Decision (B7, B8, B11, I2, J1, J2): setup installs the engines with `kmp` and `made` at `auto`, prepares MADE including `axlr_session`, and in a git workspace creates the project store from the global store's configuration, imports the bundle when present, wakes the project about and prints "N memories for project:X" or "new project, nothing recorded yet". The console start repeats the same resolution and line. The header shows the about, the memory count and the live MADE instance next to the model and workspace; `/mcp` shows per engine the store or SQLite path, the selection reason and the work identity; `/session` shows the record the console wrote for the last turn in MADE and KMP, readable, each entry with a clickable ref that opens KMP's viewer on it (J6, the viewer URL `kmp-mcp` announces on stderr); the header shows no viewer URL and there is no `/memory view`. Instances left open by a console that did not close are completed as `abandoned` at the next start in that workspace.

Engine versions (B9): always the latest release, as the installer does; [engines.lock.json](../../distribution/engines.lock.json) is the service's lock only, and the runbooks stop quoting it as the console's. MADE's store stays per user (B10), with the workspace in each instance's inputs.

Other machines and people (I3, I4, I5): memory travels with the repository's bundle (`/memory save`, then git by the person); sessions travel too, through `/session export <id>` (transcript, labels, the MADE instance id and its state) and `axlr-tui --import <file>`, which resumes on another machine with a handoff record. Several people on one project means a KMP store shared through gRPC with the project about in common and one `user:<name>` each; out of scope for now.

Verification (J3, J4): one integration test per row of the lifecycle table, with real engines in a temporary HOME, that starts the console, sends prompts and checks MADE and KMP, run in CI where the binaries are available; plus one tmux session on claude-haiku-5.5 and one on glm-5.3-flash per phase, reviewed by hand.

### D8. What the model sees

The system prompt's KMP and MADE paragraphs and the session guidance become this, under 1 KB, stable across sessions:

> Memory (KMP): the console recalled this workspace's memory in the `[AXLR · recall]` note of your first prompt and records every turn of this session itself. You never register, wake or page KMP for bookkeeping. For a specific question, `axlr_recall`; UNKNOWN is a valid answer, never invent a memory. Give each write, edit, command and external call a one-sentence `why` (for example "run the unit tests of the parser after the fix"); a call without it is refused. When the person or the repository's instructions name a KMP about, save it with `axlr_session`; after the second prompt, give the session a short title with it.
>
> Ceremonies (MADE): the console runs them, this session included; you cannot start, claim or transition one. Read definitions and instances when the task needs them; to run or publish one, tell the person to use `/ceremony`.

Where Jev is off, one more sentence: "When the work settles a decision, constraint, fix or outcome worth reusing, record it with `axlr_remember` (with `summary_en` when you wrote it in another language) before your final answer and say what you recorded, or that nothing durable came out." Driven modes keep their paragraphs. The `axlr:axlr-session` skill is removed; its inter-about reference becomes the text behind `/memory compare`.

### D9. A clean install is autonomous and completely configured

Decision (K5a, K5b, K5c): the assistant asks two things, the model (OpenRouter key or local server, skipped when `OPENROUTER_API_KEY` is set) and, optionally, the TypeSafe key for Jev; the language is taken from the environment (`LANG`), as `setupLanguage` already does for the assistant itself. Everything else is decided and shown in the startup line: both engines downloaded, stores created with their default configuration, grants and definitions published, `kmp` and `made` at `auto`, `autonomous: true`, `engines.shared: true`, forged tools on, Jev on when its key exists. `settings.json` is written complete, every section present with its value, so the person edits it without the reference; `mcp.json` is written by AXLR with mode 0600 and never by hand.

Autonomy keeps a card for the destructive list, maintained by AXLR in settings (`approvals.always_ask`) and applied to `local_exec` and bridged calls by program and arguments: deletions and overwrites outside the workspace (`rm`, `rmdir`, `mv`, redirections to paths outside the root); `git push`, `git reset --hard`, `git clean`, `git branch -D`, `git rebase`; network calls with effect (`curl`/`wget` with `-X POST|PUT|DELETE` or `--data`, `gh pr create`, `gh release`, deploy commands, anything that pays). MADE's human guards and a ceremony's first check command keep their cards as today.

### D10. The model's context is bounded in tokens, never compacted in place

Decision (K5d): the projection budget is counted with tiktoken's `o200k` encoding as the single measure for every model, replacing the bytes-per-token calibration ([bytes_per_token.go](../../tui/domain/bytes_per_token.go)); the provider's own count may differ by a tenth or a fifth and the cap absorbs it. A request's context (system prompt, tool schemas, projected messages) never exceeds 75 000 tokens (`context.max_tokens`, configurable). The prefix is kept intact: no turn is dropped and no checkpoint replaces earlier messages, so the provider's prompt cache survives every request; the recall note is appended once to the first prompt and never rewritten. When the next request would exceed the cap, the console closes the turn, completes the session's instance with a successor, starts a successor session whose first prompt carries the wake of `ws:<previous session>` and of the project about, says so in the conversation and in the header, and the old transcript stays whole and resumable. The Mac run of 13 October lost its cache at the compaction of 09:30 (cached tokens from 64 905 to 7 881) and the design removes that path.

The session cost ceiling in USD (`max_session_usd`) stays as it is, without a default; the token cap is the limit. Command timeouts keep today's values (unanswered).

## Present-tense defects found on the way

- `project:AXLR` and `project:axlr` coexist in the global store (30 and 27 events); sessions wake one and miss the other.
- Ceremony outcomes under `ws:<session-id>` are never woken by a later session (kept as the design's session about; the project receives them through Jev).
- In normal mode the model starts and transitions MADE ceremonies itself (session `e45c46dc…`); with autonomy on, without a card.
- `axlr_remember` sends no `summary_en`, and KMP's strict write requires one "when the memory is not written in English" (KMP 0.25.0 README), whatever the store's configuration: on 11 October at 20:14 claude-haiku-5.5's `axlr_remember` in session `3dd2d526…` was refused with "strict kmp_write_memory requires summary_en: summary leans to spanish" and succeeded only on a second, English, attempt; the Mac's fresh store refused the same way on 13 October at 09:37:10. The console's ceremony `RecordLinked` omits it for the same reason and is exposed the same way whenever a `summary_en` the model wrote is not English.
- A hand-edited `mcp.json` with mode 0644 stops the console at start with "run chmod 600"; the console could set the mode itself, since it owns the file, or setup could write the entries so nobody edits it by hand (the Mac, 13 October, 11:56, twice).
- The first start on a machine with no key dies with "no model provider" instead of the assistant when the build predates #115; the Mac's install channel (a binary built from `main` at 32edbe2) needs the release's build or `/update` to reach it.
- The repository's `.kmp/memory.jsonl` is untracked, so no clone receives it.
- Lock file and runbooks name engine versions the installer does not install (resolved by B9: the installer is right, the docs change).

3. **Console-owned KMP protocol** (D3, D8): registration, context injection, recall note, `axlr_recall`, `summary_en`, prompt rewrite, skill removal.
   Landed on 13 October 2026, with these notes: the session's context is kept in its `.instance` sidecar and opened at the first prompt, before the recall, with KMP alone (MADE adds the instance); the agent registry (`<state>/axlr/kmp-agents.json`) is keyed by the resolved store path, and an agent the store no longer knows is registered again; a `context_id` the model names is replaced by the session's; a store without the guide is synced when the console's own `kmp_guide` meets the refusal; `kmp_wake` and `kmp_ask` through the bridge still answer `not_found` for a missing about, the recall note and `axlr_recall` say "nothing recorded"; the re-wake rule is lexical until Jev (phase 4): a prompt sharing fewer than a fifth of its words of four letters or more with the last woken prompt gets a fresh note, one under four such words continues the topic; a resumed session's note wakes `ws:<id>` only, the MADE state and the last prompt and answer of D5 wait for phase 5; the memory reminder follows F2 (a file written or a command run) until Jev settles turns; the MADE paragraph says "ask the person" until `/ceremony` exists; the shipped prompt text is a shorter form of the D8 quotes (1 015 bytes with the record sentence and the session line); the `user:<login>` about takes the account's user name.
4. **Jev** (D5) and the MADE surface (D6): verb filter, status reports, lease renewal, handoff, `/ceremony` and publication after their spike.
   Landed on 13 October 2026, with these notes: the MADE verb filter lives where the bridge resolves plugin calls and in `axlr_tools`, not in `ModelTools`, which never carries plugin tools; MADE accepts a status report only from the claim's owner, so the lease owner of every claim is the work identity and the install id travels in the incarnation; the operation id a report needs comes from `made_inspect_ceremony_resume` (one call per claim); the finished report goes before the completion; MADE 0.10.0 answers every report with a status-claim conflict and has no grantable action for `record_ceremony_host_handoff` (its authorization checks that name, which `made_issue_authorization_grant` does not accept), so both are logged refusals until the engine changes; `discover_capabilities` and `get_help` are not grantable actions either; the handoff is detected from the sidecar's claim incarnation, not from MADE's agent roster, which stays empty; the close entry is an `observation` labelled `event=closed` (KMP has no `session_closed` kind); Jev selects rather than writes (TypeSafe answers yes/no and choice), so the settled memory is a sentence of the model's answer chosen by Jev, with an English frame as `summary_en`; `/ceremony` reads each step's `config.prompt` from the definition, since `made_explain_ceremony_draft` is refused under the work grant, and `gopkg.in/yaml.v3` parses it; the model's `/ceremony publish` stays the person's.
